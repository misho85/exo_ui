# Security Audit

## Score: 82/100

## Issues Found

- [HIGH] **Atom exhaustion via String.to_atom/1 in icon/1** (lib/exo_ui/components.ex:1409). The icon/1 component converts the user-provided name attribute to an atom via String.replace("-", "_") |> String.to_atom(), then calls apply(ExoUI.Lucide, icon_fn, ...). If a consuming app passes user-controlled input as the icon name (e.g., from a database field or URL param), an attacker can create arbitrary atoms, leading to atom table exhaustion (DoS). The atom is also used to dynamically call a function on ExoUI.Lucide, so a non-existent icon name will raise an UndefinedFunctionError rather than a clear validation error. Fix: Use String.to_existing_atom/1 instead. All 1701 icon names are loaded at compile time, so to_existing_atom will work for all valid names and raise ArgumentError for invalid ones.

- [LOW] **raw/1 used for SVG path rendering** (lib/exo_ui/lucide.ex:3315). The raw(paths) call bypasses HTML escaping for SVG path data. This is safe only because the paths come from the compile-time @icon_paths module attribute (a hardcoded map of 1701 static SVG path strings generated by mix lucide.gen). No external input can reach this code path. However, if the code generation pipeline were compromised or a developer manually edited the map, malicious SVG content could be injected. Acceptable risk for an auto-generated file.

- [LOW] **Theme toggle allows arbitrary data-theme attribute values** (assets/js/hooks/theme_toggle.js:38). The _apply method sets root.setAttribute('data-theme', theme) where theme comes from localStorage. While this is client-side only and data attributes are not executable, a malicious script with localStorage access could set unexpected theme values. Standard client-side state management, not a practical vulnerability.

## Clean Areas

- All HEEx templates use {...} interpolation (auto-escaped by Phoenix), no raw/1 in components.ex or charts.ex
- No raw/1 usage with any user-provided content; the only raw/1 is for compile-time static SVG paths
- No hardcoded secrets, API keys, or tokens found anywhere in the codebase
- No .env files present in the repository
- mix hex.audit reports zero retired packages; all dependencies are current stable releases
- All 7 JS hooks are purely UI-focused (keyboard nav, popover state, theme toggle, positioning) with no unsafe DOM patterns
- {@rest} global attribute spreading is safe because Phoenix LiveView restricts spreads to known safe HTML attributes
- Charts module generates SVG entirely from numeric computations with no string interpolation of external input
- Slot rendering via render_slot/1 is properly escaped by the Phoenix template engine
- No database queries, no Ecto, no user authentication logic (appropriate for a component library)
- Dependencies are minimal and appropriate: phoenix, phoenix_html, phoenix_live_view, gettext, plus dev/test-only deps

## Recommendations

1. Replace String.to_atom/1 with String.to_existing_atom/1 in lib/exo_ui/components.ex:1409. All 1701 Lucide icon atoms are already in the atom table at compile time, so to_existing_atom will work for all valid icon names and raise ArgumentError for invalid ones, preventing atom table exhaustion.

2. Consider adding an explicit validation in icon/1 against the known icon names before the atom conversion, providing a clearer error message rather than an UndefinedFunctionError or ArgumentError.

3. Document the security contract for the icon/1 component: consuming apps should not pass raw user input as the name attribute without validation, since calling arbitrary functions on the Lucide module is undesirable.

4. Run mix hex.audit in CI to catch future dependency retirements early.
